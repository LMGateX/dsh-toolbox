# Architecture and cross-lane contracts

## Deep modules

Feature modules hide implementation behind the existing Cordis plugin interface (name/inject/Config/apply). The Toolbox host owns orchestration, not feature policy. Browser settings and chime use native client modules and configForms/slots. Shared code is introduced only for actual repeated behavior.

## Canonical configuration

The root namespace has modules keyed context, retry, chime, goalWait. Each module value is { enabled: boolean, ...originalFeatureFields }; original chime.enabled remains the same flag, not a second nested switch. Defaults come from the feature's Config/resolveConfig. Root orchestration metadata is separate from user feature fields. Existing scalar/array zero, false and empty values must survive mapping. Arrays replace rather than concatenate.

Combined row/package id: dsh-toolbox. Split row/package ids: dsh-toolbox-context, dsh-toolbox-retry, dsh-toolbox-chime, dsh-toolbox-goal-wait. Splits may use the same canonical envelope with only their supported module in their schema. The browser selects a distribution by package/row identity and module selection, not by global singleton assumptions.

Feature code location: src/modules/context, src/modules/retry, src/modules/chime, src/modules/goal-wait. Each exposes index.ts. Adapt original feature-only code and focused regression tests here. Feature modules never directly edit profiles or disable other distributions.

Host orchestration and configuration: src/index.ts, src/config.ts, src/runtime.ts (integration owner). Migration: src/migration/* (migration lane). Browser code: client/* (client lane). Build/packaging/scripts/CI and public docs (integration owner). Agents may propose contract amendments but must coordinate shared file changes.

## Migration seam

Migration planning is pure and accepts detached discovery snapshots (profile identity, owner entries and versions, inherited/explicit config, disabled/live state, target selection and explicit target settings). Its result is per-module import/skip/conflict with reasons. Execution accepts injected storage, lock and host adapters; writes a journal before changes, revalidates snapshots and verifies actual lifecycle results. The native adapter is profile-scoped and uses host configuration/management contracts. Export a narrow public entry for inspect/dry-run/recovery; integrate with deferred host bootstrap, never package postinstall.

Integration will adapt the migration lane's exported concrete contract rather than duplicate it. The migration lane must publish interface names to the parent before writing the native adapter. Avoid nested native HMR exclusive operations or waiting for the current Loader task from inside itself.

## Distribution

One source tree, one synchronized version, five self-contained tarballs generated by scripts. Runtime host imports stay external; do not bundle a second Cordis/service registry. Split artifacts contain only their selected feature code/assets plus common orchestration/migration support. Preserve MIT source attributions and CC0 sound notices. No credentials or machine-specific paths in emitted runtime code. Tests may locate a host using an explicit environment variable.

## Testing seams

Inject host ports for planner/executor fault tests. Test features at their exported plugin interfaces. Use real published baseline host packages in disposable process/HOME/profile for native composition/reload tests. Exercise generated packed client code using browser-compatible module loading; browser integration must not reuse the live GUI URL. Verify every .tgz in a clean consumer and check its actual file list, imports, exports, bundle patch and sound assets.
